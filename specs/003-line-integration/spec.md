# Feature Specification: LINE 整合功能

**Feature Branch**: `003-line-integration`  
**Created**: 2026-01-11  
**Status**: Draft  
**Input**: User description: "顧客問題紀錄追蹤網站追加需求 - LINE 整合功能。針對已完成的顧客問題紀錄追蹤網站進行功能追加，新增 LINE 官方帳號整合功能，提升系統即時性與使用便利性。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - LINE 官方帳號綁定 (Priority: P1)

處理人員可以將其系統帳號與 LINE 官方帳號連結，建立身份關聯。使用者登入系統後，點擊「綁定 LINE 官方帳號」按鈕，系統引導加入官方帳號並完成綁定流程。綁定後，介面顯示綁定狀態，並可隨時解除綁定。

**Why this priority**: 這是 LINE 整合的基礎功能，必須先完成帳號綁定才能使用後續的推送通知和 LINE 端回報功能。沒有此功能，其他 P2 和 P3 的功能都無法運作。

**Independent Test**: 可透過以下方式獨立測試：處理人員登入系統，點擊綁定按鈕，掃描 QR Code 加入 LINE 官方帳號，系統記錄綁定關係，介面顯示「已綁定」狀態。可獨立驗證綁定和解綁功能完整性。

**Acceptance Scenarios**:

1. **Given** 使用者已登入系統且尚未綁定 LINE，**When** 點擊「綁定 LINE 官方帳號」按鈕，**Then** 系統顯示 LINE 官方帳號的 QR Code 或連結供使用者加入
2. **Given** 使用者已加入 LINE 官方帳號，**When** 在 LINE 中完成身份驗證，**Then** 系統建立使用者帳號與 LINE 帳號的對應關係並顯示「綁定成功」訊息
3. **Given** 使用者已完成 LINE 綁定，**When** 使用者查看個人設定頁面，**Then** 介面顯示「已綁定」狀態及綁定的 LINE 顯示名稱
4. **Given** 使用者已綁定 LINE 帳號，**When** 點擊「解除綁定」按鈕並確認，**Then** 系統移除帳號對應關係並顯示「未綁定」狀態
5. **Given** 使用者為訪客帳號（Guest role），**When** 嘗試存取綁定功能，**Then** 系統拒絕操作並顯示「訪客帳號無法使用此功能」訊息

---

### User Story 2 - 新增回報單時的自動推送通知 (Priority: P2)

當系統新增問題回報單並指派給處理人員時，已綁定 LINE 的處理人員會立即收到 LINE 推送訊息，包含回報單的關鍵資訊和快速連結按鈕，讓處理人員能即時掌握新問題並快速查看詳情。

**Why this priority**: 此功能顯著提升問題處理的即時性，讓處理人員不需持續登入系統查看，透過 LINE 即可即時收到通知。這是 LINE 整合的核心價值之一，但必須在 P1 綁定功能完成後才能運作。

**Independent Test**: 可透過以下方式獨立測試：建立新的問題回報單並指派給已綁定 LINE 的處理人員，驗證該處理人員的 LINE 是否收到格式正確的推送訊息，訊息包含所有必要資訊，快速連結按鈕可正常開啟回報單詳細頁面。

**Acceptance Scenarios**:

1. **Given** 處理人員已綁定 LINE 帳號，**When** 系統新增一筆問題回報單並指派給該處理人員，**Then** 該處理人員的 LINE 立即收到推送通知訊息
2. **Given** 推送訊息已送達，**When** 處理人員查看訊息內容，**Then** 訊息包含回報單編號、問題標題、緊急程度、問題所屬單位、聯絡人、連絡電話、紀錄日期、回報人等完整資訊
3. **Given** 推送訊息包含快速連結按鈕，**When** 處理人員點擊「查看回報單詳情」按鈕，**Then** 系統開啟該回報單的詳細頁面
4. **Given** 處理人員尚未綁定 LINE 帳號，**When** 系統新增回報單並指派給該處理人員，**Then** 系統不發送 LINE 推送訊息（僅透過網頁端通知）
5. **Given** 一筆回報單同時指派給多位處理人員，**When** 回報單建立完成，**Then** 所有已綁定 LINE 的處理人員都會收到推送通知

### User Story 3 - LINE 端回報問題 (Priority: P3)

已綁定系統帳號的使用者可直接在 LINE 官方帳號中回報問題，無需登入網頁系統。使用者在 LINE 輸入「回報問題」或點擊快速選單，系統透過對話式介面引導填寫問題資訊，填寫完成後顯示摘要供確認，確認後自動建立回報單並同步至系統。

**Why this priority**: 此功能提供最便利的回報管道，讓使用者隨時隨地透過 LINE 回報問題，降低回報門檻。但相較於即時通知功能，此功能的優先級較低，因為網頁端回報已經存在，LINE 端回報是額外的便利性提升。

**Independent Test**: 可透過以下方式獨立測試：已綁定帳號的使用者在 LINE 中輸入「回報問題」，依照引導填寫完整資訊，確認後系統建立回報單。驗證回報單資料正確同步至網頁系統，並確認自動指派邏輯運作正常。

**Acceptance Scenarios**:

1. **Given** 使用者已綁定 LINE 帳號，**When** 在 LINE 中輸入「回報問題」或點擊快速選單按鈕，**Then** 系統回覆引導訊息，開始問題回報流程
2. **Given** 回報流程已啟動，**When** 系統依序詢問問題標題、問題內容、問題所屬單位、緊急程度、聯絡人、連絡電話，**Then** 使用者逐步填寫各項資訊
3. **Given** 系統詢問問題所屬單位，**When** 顯示選項給使用者，**Then** 選項包含系統中所有啟用的單位名稱
4. **Given** 系統詢問緊急程度，**When** 顯示選項給使用者，**Then** 選項包含「高」、「中」、「低」三個等級
5. **Given** 使用者已填寫所有必要資訊,**When** 系統顯示回報內容摘要,**Then** 摘要包含所有填寫的資訊及系統自動填入的資訊(紀錄日期、回報人、處理狀態、指派處理人員),並提供「確認送出」、「重新填寫」、「取消」三個選項
6. **Given** 系統顯示確認摘要,**When** 使用者點擊「確認送出」,**Then** 系統建立回報單並回覆回報單編號與查看連結
6a. **Given** 系統顯示確認摘要,**When** 使用者點擊「重新填寫」,**Then** 系統清除已填寫的資訊並從第一步重新開始回報流程
7. **Given** 回報流程進行中，**When** 使用者輸入「取消」，**Then** 系統中斷流程並回覆「已取消回報」訊息
8. **Given** LINE 端建立的回報單，**When** 在網頁系統中查詢，**Then** 回報單資料完整顯示且與 LINE 填寫內容一致
9. **Given** 使用者尚未綁定系統帳號，**When** 在 LINE 中嘗試回報問題，**Then** 系統回覆「請先完成帳號綁定」訊息並提供綁定指引

### Edge Cases

- **帳號綁定衝突**: 當一個 LINE 帳號嘗試綁定多個系統帳號時，系統拒絕操作並提示「此 LINE 帳號已綁定其他系統帳號」
- **綁定狀態同步**: 當使用者在網頁端解除綁定後，LINE 端的功能（如回報問題）立即失效，引導使用者重新綁定
- **併發綁定/解綁操作**: 當使用者同時在多個裝置進行綁定或解綁操作時，系統採用最後寫入優先策略，最後完成的操作生效，並記錄完整操作日誌（時間戳、IP、裝置資訊）
- **推送訊息失敗**: 當 LINE 推送訊息因 LINE 平台問題或網路問題失敗時，系統採用指數退避重試策略（最多 3 次，間隔 1 秒、5 秒、15 秒），記錄失敗日誌
- **LINE 端回報流程超時**: 當使用者在回報流程中超過 15 分鐘未回應，系統自動取消流程並提示「回報流程已逾時，請重新開始」
- **無效的資料格式**: 當使用者在 LINE 回報流程中輸入無效的電話格式或資料時，系統提示格式錯誤並要求重新輸入
- **單位無可用處理人員**: 當使用者在 LINE 端選擇的單位沒有預設處理人員時，系統建立回報單但不自動指派，並標記為「待指派」狀態
- **多單位同時指派**: 當問題需要多個單位協同處理時，系統允許在網頁端手動補充指派，所有相關處理人員都會收到 LINE 通知
- **訊息內容過長**: 當推送訊息的問題標題或內容超過 LINE 訊息長度限制時，系統自動截斷並加上「...」，完整內容需透過連結查看

## Requirements *(mandatory)*

### Functional Requirements

#### 帳號綁定相關需求

- **FR-001**: 系統必須提供「綁定 LINE 官方帳號」功能入口，位於使用者個人設定或導覽選單中
- **FR-002**: 系統必須使用 LINE Login OAuth 2.0 流程完成 LINE 帳號綁定，包含 state 參數以防止 CSRF 攻擊
- **FR-003**: 系統必須在綁定成功後建立並持久化使用者帳號與 LINE 帳號的對應關係（儲存 LINE User ID）
- **FR-004**: 系統必須在個人設定頁面顯示目前的綁定狀態（已綁定/未綁定）及綁定的 LINE 顯示名稱
- **FR-005**: 系統必須提供「解除綁定」功能，解除後清除對應關係
- **FR-006**: 系統必須限制訪客帳號（Guest role）無法使用 LINE 綁定功能
- **FR-007**: 系統必須防止一個 LINE 帳號綁定多個系統帳號，若重複綁定則拒絕並提示錯誤訊息
- **FR-008**: 系統必須在解除綁定時同步停用該使用者的 LINE 端功能（推送通知、LINE 回報）
- **FR-008a**: 系統必須記錄所有綁定和解綁操作的日誌，包含時間戳、使用者 ID、LINE User ID、操作類型、IP 位址、裝置資訊，當併發操作發生時採用最後寫入優先策略

#### 推送通知相關需求

- **FR-009**: 系統必須在新增問題回報單時，自動檢查被指派的處理人員是否已綁定 LINE
- **FR-010**: 系統必須對已綁定 LINE 的處理人員發送推送訊息
- **FR-011**: 推送訊息必須包含以下資訊：回報單編號、問題標題、緊急程度、問題所屬單位、聯絡人、連絡電話、紀錄日期、回報人
- **FR-012**: 推送訊息必須包含快速連結按鈕，點擊後開啟該回報單的詳細頁面
- **FR-013**: 系統必須支援當回報單指派給多位處理人員時，所有已綁定 LINE 的處理人員都能收到通知
- **FR-014**: 系統必須記錄推送訊息的發送狀態（成功/失敗），失敗時採用指數退避重試策略（最多 3 次，間隔 1 秒、5 秒、15 秒）並記錄錯誤原因
- **FR-015**: 推送訊息格式必須符合範例格式，包含清晰的視覺分隔線和表情符號標示

#### LINE 端回報相關需求

- **FR-016**: 系統必須在 LINE 官方帳號中提供「回報問題」關鍵字觸發或快速選單按鈕
- **FR-017**: 系統必須透過對話式介面依序引導使用者填寫：問題標題、問題內容、問題所屬單位、緊急程度、聯絡人、連絡電話
- **FR-018**: 系統必須在詢問問題所屬單位時，提供系統中所有啟用單位的選項清單
- **FR-019**: 系統必須在詢問緊急程度時，提供「高」、「中」、「低」三個選項
- **FR-020**: 系統必須自動填入以下資訊：紀錄日期（當前時間）、回報人（從綁定帳號取得）、處理狀態（預設為待處理）、指派處理人員（根據所選單位的預設處理人員）
- **FR-021**: 系統必須在使用者填寫完成後,顯示完整摘要供確認,包含所有填寫及自動填入的資訊,並提供「確認送出」、「重新填寫」、「取消」三個操作選項
- **FR-022**: 系統必須在使用者確認後建立回報單並同步至資料庫
- **FR-022a**: 系統必須在使用者選擇「重新填寫」時,清除當前對話狀態並從第一步重新開始回報流程
- **FR-023**: 系統必須在回報單建立成功後，回覆使用者回報單編號與查看連結
- **FR-024**: 系統必須允許使用者在填寫過程中輸入「取消」中斷流程
- **FR-025**: 系統必須驗證使用者已綁定系統帳號，未綁定者無法使用 LINE 端回報功能
- **FR-026**: LINE 端建立的回報單必須與網頁端建立的回報單功能完全相同，立即同步且無差異
- **FR-027**: 系統必須驗證使用者輸入的資料格式（例如電話號碼格式），格式錯誤時提示重新輸入

#### 資料驗證與錯誤處理

- **FR-028**: 系統必須驗證必填欄位完整性，缺少必填資訊時提示使用者補充
- **FR-029**: 系統必須處理 LINE 平台 API 呼叫失敗的情況，記錄錯誤並提供適當的使用者回饋
- **FR-030**: 系統必須處理回報流程超時情況，自動取消並提示使用者
- **FR-031**: 系統必須自動清理已完成或已取消的對話狀態資料，保留期限為 24 小時

### Key Entities

- **LineBinding（LINE 綁定關係）**: 記錄系統使用者帳號與 LINE 帳號的對應關係，包含系統使用者 ID、LINE User ID、綁定時間、LINE 顯示名稱、綁定狀態（啟用/已解除）
- **ConversationState（對話狀態）**: 記錄 LINE 端回報流程的對話狀態，包含 LINE User ID、當前步驟、已填寫的資訊、最後互動時間，用於支援多步驟對話流程。對話完成或取消後保留 24 小時以便除錯和審計
- **PushNotificationLog（推送通知日誌）**: 記錄推送訊息的發送歷史，包含回報單 ID、接收者 LINE User ID、發送時間、發送狀態（成功/失敗）、錯誤訊息（若失敗）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者能在 2 分鐘內完成 LINE 帳號綁定流程，成功率達 95% 以上
- **SC-002**: 處理人員在回報單建立後 10 秒內收到 LINE 推送通知，推送成功率達 98% 以上
- **SC-003**: 使用者能在 3 分鐘內透過 LINE 完成問題回報，包含所有必填資訊的填寫和確認
- **SC-004**: LINE 端建立的回報單與網頁端即時同步，資料一致性達 100%
- **SC-005**: 推送訊息包含所有必要資訊且格式正確，使用者無需額外詢問即可理解問題概況
- **SC-006**: 快速連結按鈕點擊後能在 3 秒內開啟對應的回報單詳細頁面
- **SC-007**: 90% 的處理人員在收到 LINE 通知後 30 分鐘內查看回報單詳情，相較於僅網頁通知提升響應速度 50%
- **SC-008**: 系統支援至少 100 位使用者同時進行 LINE 回報流程而不發生效能降低
- **SC-009**: LINE 整合功能上線後，透過 LINE 回報的案件佔總回報量的 30% 以上，顯示功能實用性
- **SC-010**: 綁定狀態變更（綁定/解綁）後，相關功能權限在 1 秒內生效

## Clarifications

### Session 2026-01-11

- Q: LINE 帳號綁定時的身份驗證流程應該如何設計？ → A: 使用 LINE Login OAuth 2.0 流程搭配 state 參數防止 CSRF 攻擊
- Q: 當 LINE 推送訊息失敗時，系統應該採用什麼重試策略？ → A: 採用指數退避重試策略，最多重試 3 次，間隔為 1 秒、5 秒、15 秒
- Q: LINE 端對話狀態（ConversationState）資料應該保留多久？ → A: 對話完成或取消後保留 24 小時，以便除錯和審計
- Q: 當使用者在 LINE 回報流程中填錯資訊，應該如何修正？ → A: 在最終確認摘要時提供「重新填寫」按鈕重頭開始
- Q: 當使用者同時在多個裝置或瀏覽器中進行 LINE 帳號綁定/解綁操作時，系統應該如何處理？ → A: 採用最後寫入優先（Last Write Wins）策略，並記錄操作日誌
